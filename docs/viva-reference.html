1. Project overview (30-second pitch)

FarmSense AI is a mobile-first web application that helps smallholder / small-scale farmers choose crops using soil suitability, weather fitness, price outlook, and demand / oversupply signals — not soil alone. Farmers enter N, P, K, pH (and location), get ranked crop plans with explainable scores, can confirm a plan, set a planted date for harvest/sell reminders, and see district-level overcrowding risk.

Who

Smallholders / allotment-scale growers in a UK-focused demo context (GB district + temperate crop filter).

What

End-to-end SPA + API + Postgres + trained ML artefacts in Docker.

Gap

Most crop ML apps stop at soil/climate. Few join market timing + local oversupply.

2. Problem, aim, research questions

Problem

  • Crop choice is often habit-based, not evidence-based.
  • Soil-only recommenders ignore price windows and local gluts.
  • Market / weather data exists (DEFRA, GOV.UK, Open-Meteo) but is hard to use as one decision tool.

Aim

Design and evaluate an integrated crop-planning system that ranks crops by suitability and short-horizon market/weather context, with oversupply awareness.

Typical research questions (proposal / dissertation)

  1. Does a multi-layer pipeline (soil + weather + price + demand) change recommendations vs soil-only?
  2. Can public search-interest signals add useful demand context (and when do they fail)?
  3. Can LSTM forecasts beat simple baselines (e.g. ARIMA) on price series for the project horizon?

Why JSONB for ranked_output?

ML outputs are nested (crops, factor scores, planting windows, planted date, sources). JSONB keeps schema flexible while still queryable, without dozens of child tables for every UI field. Core relational facts (who, farm, confirmations, aggregates) stay normalised.

Migrations

  • 004_crop_lifecycle.sql — days_to_harvest / days_to_sell on crops
  • (others) preference flags and incremental upgrades for existing DBs

UK crop filter

For GB farms, tropical RF classes (e.g. rice/banana if present in the training set) are down-weighted or filtered so recommendations stay temperate-relevant.

Oversupply

Confirmed plans increment district_crop_aggregate. Risk rises when many farmers in the same district lock the same crop (threshold configurable, default around 100 plans). Shown on community / ranking paths — this is the “don’t all plant the same thing” feature.

8. Why Random Forest (and why LSTM elsewhere)

Why Random Forest for soil?

  • Tabular data: N,P,K,pH, temperature, humidity, rainfall suit tree ensembles.
  • Accuracy: Literature + this project’s test set (~97.5%) beat the ≥85% NFR.
  • Robustness: Less prone to overfitting than a single deep tree; handles mixed feature scales.
  • Deployability: One .pkl via joblib — no GPU needed for inference.
  • Explainability: Feature importance supports “why this crop?” narratives.

Why not RF for price/weather?

  • Price and weather are sequences — order matters.
  • LSTM captures temporal dependence; ARIMA is the classical baseline.
  • Project result: LSTM price MAPE lower than ARIMA on held-out series.
  • At serve time, official GOV.UK/Defra indices can override/blend so farmers see UK-grounded prices.
Short viva line: “Random Forest for static soil–climate suitability; LSTM for time-series weather and price; public demand signals and district counts for market crowding — then a weighted rank.”

Alternatives considered (say this if asked)

  • SVM / k-NN for soil — common in papers but RF usually stronger/more stable on this dataset style.
  • ARIMA-only price — simpler but worse MAPE here; kept as baseline.
  • Paid market APIs — rejected for cost; open UK sources preferred.
  • Reddit NLP as primary demand — proposed early; production prioritises Trends + Wikipedia and refuses fake scores when APIs fail.

14. Limitations (say these confidently)

  • Soil training set is a public crop-recommendation dataset — not UK farm soil lab results.
  • RF classes include non-UK crops; mitigated by GB filters, not by retraining on UK-only labels.
  • Demand (Trends) is a proxy for interest, not confirmed purchase volume; correlation with price can be weak.
  • LSTM horizons are short (weeks); not a full agronomic DSS.
  • Oversupply depends on users confirming plans in-app — cold start if few users.
  • Email reset needs Resend key; without it, reset is limited.
  • Not financial advice — decision support only.

15. Viva Q&A bank

Search questions below. Click a row to expand the answer.

What is FarmSense AI in one minute?
A full-stack crop planning app: farmers enter soil and location; a Random Forest scores suitability; weather and price layers (LSTM + open UK/weather data) and demand/oversupply signals adjust ranking; results are stored as plans in PostgreSQL via FastAPI, shown in a React SPA.
Why is this project needed?
Smallholders often choose crops by habit. Soil-only ML tools ignore market timing and local gluts. Open UK price and weather data exist but are not joined into one farmer-facing decision flow. FarmSense AI bridges that gap.
What is your main contribution?
An integrated multi-layer ranking pipeline (soil + weather + price + demand) with district oversupply awareness and explainable UI — not just another soil classifier. Also an end-to-end deployable system (Docker + SPA), not only notebooks.
Walk me through the architecture.
Browser React app talks REST/JWT to FastAPI. FastAPI uses SQLAlchemy against PostgreSQL. On recommend, it loads rf_suitability.pkl, scores weather/price layers (LSTM + Open-Meteo / GOV.UK), blends demand and district aggregates, writes recommendation_run.ranked_output JSONB, returns ranked crops to the UI.
Why did you choose Random Forest?
Soil features are tabular; RF handles non-linear interactions without heavy preprocessing, performed ~97.5% accuracy on the held-out suitability set (above 85% NFR), ships as a small pickle for CPU inference, and gives feature-importance style explanations. SVM/k-NN are common alternatives but RF was stronger/stabler for this use case.
Why LSTM for weather and price?
Those are time series. LSTM captures temporal patterns better than treating weeks as independent rows. Literature often prefers LSTM/GRU over classical ARIMA for agricultural prices; in this project LSTM price MAPE beat ARIMA (~4.96% vs ~9.55%). Weather LSTM is blended with live Open-Meteo for current conditions.
How do you combine the layers into one score?
Weighted confidence ≈ 0.35×soil + 0.22×weather + 0.28×price + 0.15×demand (capped), then profit-style ranking for display order. Weights reflect that soil fitness is foundational but market/price matter for the project’s aim. Training also explored XGB ranking (metrics_e).
You mentioned NLP / Reddit / Trends — what actually ships?
Early proposal explored NLP/Reddit. The live product prioritises free Google Trends (GB) with Wikipedia pageviews fallback, plus district planting share. If signals fail, the UI shows unavailable rather than fabricating demand. An NLP experiment remains in metrics_d for the research trail.
How does oversupply detection work?
When a farmer confirms a crop plan, counts update in district_crop_aggregate. High local counts raise risk (low/medium/high). That risk influences messaging and can affect ranking so the system discourages everyone planting the same crop in one district.
Why PostgreSQL and why JSONB?
Users, farms, soil readings, and confirmations need relational integrity and aggregation. Ranked ML payloads are nested and evolve with the UI, so ranked_output JSONB stores flexible plan detail without constant schema migrations, while foreign keys keep the core model clean.
Why FastAPI instead of Node/Django?
ML stack is Python (scikit-learn, TensorFlow). FastAPI keeps inference and API in one language, gives automatic OpenAPI docs for demos, and Pydantic validation. Django would be heavier for a JSON API; Node would force a second language around model loading.
Why React and Zustand?
React fits a rich SPA (dashboard, plans, charts). Zustand is a small persisted store for auth token and farm/plan state — enough without Redux boilerplate. Vite speeds local development for iterative UI work.
How do you run and demonstrate the system?
docker compose up builds Postgres on 5433 and API on 8000 with ML artefacts mounted. npm run dev serves the SPA on 5173 with VITE_API_BASE_URL pointing at the API. Show /health/ready, then soil → recommendations → plant date → confirm → community/dashboard.
How is security handled?
Passwords hashed with bcrypt; sessions via JWT Bearer tokens; role checks for admin; SlowAPI rate limits; idempotency keys on sensitive POSTs; CORS configured for the SPA origin. Password reset tokens stored server-side; email via Resend when configured.
Explain the planted-date / harvest schedule feature.
crop_reference stores days_to_harvest and days_to_sell ranges. crop_lifecycle_service computes windows from a planted date (user-set via PATCH /plans/{id}/schedule) or falls back to plan generated date. Dashboard/recommendations show concrete sell windows instead of hardcoded week labels.
What are Simple mode and Demo mode?
Simple mode reduces UI complexity for less technical users (preference on user_account). Demo data mode can show clearly tagged sample market/community data when live feeds are sparse — so demos stay honest.
How did you evaluate success?
Against NFRs: RF accuracy ≥85% (achieved ~97.5%); price MAPE target <15% (LSTM ~4.96%). Weather MAE/RMSE reported. Scenario checks in metrics_e compare full pipeline vs soil-only. Plus API tests, health/ready, and qualitative usability via Simple mode / mobile layout.
What are the main limitations and ethical issues?
Training data is not UK soil labs; demand proxies aren’t purchases; cold-start oversupply; forecasts can be wrong. Ethically: decision support not advice; avoid overclaiming certainty; protect credentials; label demo data; don’t fabricate market signals. Consider bias if RF was trained on non-local crops.
Your RF was trained on global crops — how do you handle UK use?
For GB country_code, ranking prefers UK-focus classes and down-weights tropical labels so rice/banana-style suggestions don’t dominate temperate farms. It’s a pragmatic filter; ideal future work is UK-labelled training data.
What development methodology did you use?
Iterative / agile-style: proposal → schema → ML notebooks → API → UI → integration → refinement (multi-plan, lifecycle, honest demand). Docker for reproducible environments. Requirements MoSCoW from the proposal guided priorities.
If you had more time, what would you improve?
UK-specific soil/crop dataset; stronger causal demand models; more robust cold-start oversupply; field trials with real farmers; CI/CD; perhaps lighter ONNX export instead of TensorFlow in Docker; accessibility audit and more automated E2E tests.
Where is the recommendation logic in the repo?
Primary: backend/app/services/recommendation_service.py. ML load: app/ml/loader.py. Layer scoring: app/ml/pipeline_layers.py and lstm_inference.py. Demand: demand_signals_service.py. Lifecycle: crop_lifecycle_service.py. Schema: database/init.sql.
What can an admin do?
View overview/analytics, manage/list farmers, inspect model layer status and run lab tests — useful to show examiners that ML health is observable, not a black box only on the farmer UI.
What external data sources do you use?
Open-Meteo for live weather/agri indicators; GOV.UK / Defra-related price indices for UK market context; Google Trends and Wikipedia pageviews for demand interest; Nominatim/postcodes.io on the frontend for location helpers.
What happens when a farmer confirms a plan?
A confirmed_crop_plan row links the recommendation_run to a crop; district aggregates update; oversupply risk can change for that district/crop. The farmer keeps multi-plan history; confirmation is the signal that feeds community crowding logic.
Did you hit any notable bugs and how did you fix them?
Example: treating /auth/me HTTP 429 as logout cleared sessions during rate limiting — fixed by only clearing on 401/403. Layout issues on Recommendations (nested scroll / sticky aside) were fixed by adjusting overflow and sticky positioning rather than nested scroll containers.
Did your results support the research questions?
RQ1: metrics_e scenarios show cases where full pipeline score differs from soil-only (not always “wins,” which is itself a honest finding). RQ2: Trends–price correlation in metrics_d was often non-significant — so demand is treated cautiously. RQ3: LSTM beat ARIMA on price MAPE in metrics_b.
How do you handle personal data / GDPR-minded design?
Store minimal account data (email, hashed password, farm district). JWT sessions rather than sharing passwords. No need to store raw soil indefinitely beyond what’s needed for plans. Password reset tokens expire. For a real deployment you’d add retention policy, export/delete, and DPIA — student demo keeps scope small.
What non-functional requirements did you target?
Examples: RF accuracy ≥85%; price forecast MAPE under 15%; usable mobile-first UI; API health checks; rate limiting; Docker reproducibility. Exact wording lives in the proposal/dissertation NFR tables.
Is the system a black box?
Not entirely: UI shows factor breakdown (soil/weather/price/demand percentages and plain-language blurbs). RF is more interpretable than deep nets for soil. LSTMs are less transparent, so we report metrics and blend with official price indices where possible.
